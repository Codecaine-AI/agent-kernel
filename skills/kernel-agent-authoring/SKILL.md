# Kernel Agent Authoring

This skill is a router: the model, the orientation procedure, and the
cross-artifact invariants live here; everything else routes to the authoring
docs in References. Do not answer bundle questions from memory when a
referenced doc owns the topic.

## The Model

- Every request an agent sees is three sections: ① system prompt · ② one
  context message of standing blocks · ③ rendered state + conversation tail.
- ① is `prompt/system.md`, GENERATED from `prompt.json` (the source of truth).
- ② is standing reference material: the context sidecar declares loaders and
  assembles their results into named blocks. It does not move during a run.
- ③ is the moving work picture: the state sidecar's `S` is seeded once per
  spawn from `SpawnContext` (seed-once contract), updated per session event,
  and re-rendered into the request every turn.
- A bundle is one folder: `agent.json` + `prompt/prompt.json` →
  `prompt/system.md` + `context/index.ts` + `tools/index.ts` +
  `state/index.ts` (+ `state/fixtures/*.json`). Each section may also be a
  single file (`context.ts`); when both forms exist the file wins.

## Orient — do this first, every session

1. Preferred: run the deterministic brief from this skill directory —
   `bun scripts/brief.ts [start-dir] [agent-name]`. It walks up from the
   start dir (default cwd) to `.agent-kernel/kernel.json`, reads
   `catalogRoots`, and prints every bundle's anatomy, assembled ② blocks,
   and a rendered ③ fixture.
2. By hand when the brief cannot run: find `.agent-kernel/kernel.json` from
   cwd upward → open each `catalogRoots` entry → per bundle read
   `agent.json`, `context/index.ts` (or `context.ts`), `state/index.ts`
   (or `state.ts`).
3. Read the app's own agent docs when the repo ships them (e.g.
   `canvas/docs/30-agent-layout/`). App docs outrank general intuition about
   what a block or render is for.

## Invariants

- `prompt/system.md` and `prompt.rendered.md` are generated — NEVER
  hand-edit. Regenerate: `bunx agent-kernel-render-prompts <catalog-root>`
  (or `--agent <bundle-dir>`). Structural `prompt.json` edits belong to the
  prompt lab flow, not ad-hoc JSON surgery.
- State `S` must stay JSON-serializable — the kernel snapshots it to
  `state.json` and treats it as opaque. This is why app-side registries
  exist: live objects stay in the app, ids ride in `S`.
- Changing what a state `render` emits requires updating the matching ②
  grammar/context block in the same change — otherwise the prompt lies about
  the state the model will see.
- `*.generated.ts` files are regenerated by their generator — never edited
  by hand.
- ② is standing material, ③ is moving material. Do not smuggle one into the
  other; the boundary is the request contract.
- Declare `host: "any"` in `agent.json` only when every sidecar is
  Node-portable (no bun-only APIs, no app-service imports) — the doctor's
  host portability check verifies it. The default (no field) is app-hosted:
  standalone harnesses classify the bundle without evaluating it.

## Verify

1. Typecheck (the repo's own typecheck target).
2. `bunx agent-kernel-doctor --catalog <catalog-root ...>` — bundle-layout
   problems (shadowed forms).
3. `bunx agent-kernel-render-prompts --check <catalog-root>` — stale prompt
   snapshots.
4. Re-render a state fixture and READ the output — `bun scripts/brief.ts
   <repo> <agent>` prints it. A render that types but reads wrong is still
   wrong.
