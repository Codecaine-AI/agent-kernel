Prompt layers & where state lives

Agent Kernel design explainer — companion to context-fold-projection.html — 2026-07-25

TL;DR. Order the compiled request by how fast each part changes — system prompt, then capabilities, then state, then history, then the live turn. That ordering is good design on its own (stable things stay put, volatile things stay at the edge); caching happens to reward it, but we're not designing around caching right now. The bigger open question is where the run's state actually lives on disk. Today the durable trace DB and the disposable session JSONL sit in the same .agent-kernel/ directory. Those two have opposite lifetimes, and in a wipe-after-run sandbox that co-location is the thing that breaks.

Updated by the 2026-07-27 design interview. The state model now lives in state-shapes.html (v4): one state object per agent (messages included), a seed / update / render contract, and a three-section request. §7's options table below is superseded — there is no kernel reducer schema and no kernel remember tool; each agent's state.ts owns shape, update rules, and render. This doc remains the home of the storage layout and the transport design; the agreed transport decisions are pinned at the end of §9.

3. The problem in one line PROPOSAL

In a Daytona-style sandbox, <app-root>/.agent-kernel/ is inside the sandbox. Wipe the sandbox and you lose the JSONL, the working memory, and the trace DB — including the record of everything that just happened. The durable thing and the disposable thing are in the same folder, so the disposable one takes the durable one down with it.

The fix isn't a new format; it's a boundary. Split the directory by lifetime, and let only the durable half leave the machine.

4. Proposed: run-local vs. durable SKETCH — open

Inside the sandbox

ephemeral — assume it is lost
  • In-memory state — what the projection renders from
  • pi-sessions/**.jsonl — Pi's transcript, needed for local resume
  • state.jsonl — our append-only fold log (new)
  • <app>-sessions/** — working memory, deliverables

No DB, no network needed. The agent is fully self-sufficient here.

──▶
state channel
ordered, acked, low volume
──▶
observability channel
batched, droppable

Outside — stable infrastructure

durable — survives the sandbox
  • trace.db — moved out of the sandbox
  • state snapshots — each fold, retained
  • artifacts — deliverables worth keeping

This is what a restart rebuilds from once the sandbox is gone.

The concrete change to today's layout: trace.db stops being a sibling of pi-sessions/. Inside the sandbox the kernel writes only a local run directory; the trace DB lives wherever the receiver lives. Locally (single machine, no sandbox) the two collapse back into the same folder and nothing changes — the boundary is a deployment concern, not a code fork.

Why two channels and not one. A single stream can't be both "never blocks the agent" and "authoritative enough to rebuild from." Folds are small, ordered, and worth an acknowledgement; spans and token counts are high-volume and safe to drop. Splitting them means the 1000-agent write-contention worry lands on the cheap channel, while the channel recovery depends on stays small enough to guarantee.

Whether the state log is a separate state.jsonl or just more custom entries inside Pi's session file is a real fork worth deciding: co-locating keeps one file to ship and one thing to replay; separating keeps our format independent of Pi's and makes the state channel trivial to tail on its own.

6. Pi does not re-read the JSONL each turn SOURCE-VERIFIED

This is worth stating plainly because it removes a whole class of problem. The agent loop runs off an in-memory array; the JSONL is a write-behind log, not the loop's input.

Per turn — in memory

every request
  • agent-loop.js reads context.messages
  • new messages are push()ed onto that same array
  • the context hook rewrites a copy for the request

The JSONL is never consulted here.

▼
append-only write
write-behind log
▲
read at load only
resume · fork · switch

The JSONL

read only at session load
  • buildSessionContext() parses entries → messages
  • called at construction, resume, fork, and session switch
  • not called per turn

Historical record, not the live input.

So the image question answers itself: there is no handshake, and nothing gets removed from the JSONL.

  • Turn 3 — the browser tool returns a screenshot. The JSONL records it permanently. That is true: at turn 3, that screenshot existed.
  • Turn 10 — the context hook compiles the request, keeps the 3 most recent images, and replaces older image blocks with a text stub: [screenshot from turn 3 — superseded; call browser_snapshot for current].
  • The JSONL is untouched. The in-memory array is untouched. Only the outgoing request differs — and it is recomputed from scratch on the next request anyway.
  • After a restart — the process reloads the JSONL, gets all the images back in memory, and the context hook applies the same rule on the next request. Same three images. It self-heals; nothing needs to be pre-processed.

The one real constraint: assistant toolCall blocks and their toolResult must be dropped as pairs. Rewriting block content — an image to a stub — is unrestricted, which is exactly what image eviction needs.

The one real cost: the in-memory array grows for the life of the process even though requests stay small. That's memory pressure, not tokens — and only matters for very long-lived runs.

7. How the state actually gets built SKETCH — pick one

Four options, roughly in order of how much determinism they preserve:

ApproachHowGoodBad
A · Reducers in code agent bundle ships state.ts: (state, event) => state deterministic, free, testable, replayable only captures what you can express mechanically
B · Agent-authored an update_state / remember tool the model calls captures judgment and intent costs turns; model may forget; nondeterministic
C · Fold agent a cheap LLM call at fold time rewrites the state doc handles prose and summarization well latency on the critical path; not replayable
D · Hybrid A for structured facts, B as an explicit escape hatch deterministic core, human-legible extras two mechanisms to reason about

Recommendation: start at D — reducers plus a remember tool — and defer the fold agent until something demands it.

The argument is replayability, and it compounds with §6. Projection is already a pure function of (messages + state). If state derivation is also pure, then the whole pipeline is deterministic: given the event log, you can rebuild the exact state and the exact compiled request offline. That is what makes trace-based recovery actually work. Put an LLM inside the fold and rebuild stops being reproducible — you'd have to snapshot state rather than derive it, and every debugging session becomes archaeology.

Reducers also fit the existing typed-agent-bundle shape — agent.json + prompt.json + context.ts + tools.ts gains a state.ts sidecar. Same discovery, same validation, same authoring story.

Sketch of what a state.ts sidecar could look like — shape only, not a proposed API:

export const initialState = {
  goal: null, constraints: [], candidates: [],
  decisions: [], openQuestions: [],
};

export const reducers = {
  tool_result(state, ev) {
    if (ev.toolName !== "read_file") return state;
    return { ...state, workingSet: add(state.workingSet, ev.path) };
  },
  remember(state, ev) {           // the agent-authored escape hatch
    return { ...state, decisions: [...state.decisions, ev.text] };
  },
};

// projection reads state; it never writes it
export function renderState(state) { return xml("current_state", state); }

The point of the walkthrough. At turn 5 the fourth screenshot arrives. Nothing is deleted anywhere — the state ledger holds all four references and the JSONL holds all four images permanently. The projection keeps the newest three live and renders the oldest as a one-line stub. Change the cap to 5 and the next request simply renders differently; no migration, no rewrite, no handshake.

That is what makes the state file "the logic that shows the agent what it's doing": reducers decide what is true, projection decides what is shown, and the two are separate functions so either can change without touching the other.

9. Getting traces out — one path, both topologies SKETCH — open

Agreed on the premise: traces should be fired by our code in-process, never by reading the JSONL. That's already the decided architecture (extension-primary emission) and the spike confirmed the extension observes everything the JSONL contains, plus things it never will.

The part that needs designing is transport. The way to avoid a sandbox/local fork is to make every emit go to a local spool file, and vary only what drains it:

1 · Emit

in-process, synchronous

Extension hook appends one line to spool.jsonl. A file append — never a network call, never a DB write. Cannot block the agent, cannot fail because something else is down.

──▶
cursor

2 · Drain

async loop, tracks a cursor

Reads forward from the last committed offset, batches, hands to the sink. Advances the cursor only on success. Retries and backs off on failure.

──▶
sink

3 · Sink

the only thing that differs
  • Local: write straight into trace.db
  • Sandbox: POST batches to the receiver

Local dev and sandbox then run identical code with a different sink binding — no conditional paths in the emitter, and the durability semantics are the same in both. The spool is also what makes the two-channel split concrete: state-channel entries hold the cursor until acknowledged, observability entries can be dropped under backpressure without holding anything up.

This also removes the last reason to read JSONL for traces: the spool is the local durable buffer, so a crashed run leaves a spool to drain on restart rather than a transcript to re-derive from.

Pinned — 2026-07-27 interview.

  • One emission seam from v1: trace events, request snapshots, and state-update / state.json writes all flow through the existing TraceWriterSink-style interface. Transfer-out becomes a sink swap, not a rework.
  • Sandbox stage (build-order stage 5): spool file → drain loop → remote POST sink, built and verified working in a sandbox-type environment — not just designed.
  • Two channels: the state channel is acked and deduped on the state version; the observability channel is droppable under backpressure. Ack/backpressure specifics are decided at the sandbox stage.
  • v1 storage: state.json snapshot per update batch under .agent-kernel/state/<container>/<agent>/; no action log, no artifact byte-store yet.

10. Open questions ? OPEN

  • One file or two? Kernel state as custom entries inside Pi's JSONL, or a sibling state.jsonl we own end to end.
  • Where does trace.db go in a sandbox? If the receiver is remote, is there still a local DB at all, or only a spool file that drains outward?
  • What does a restart actually need? Enough state to continue the task, or a byte-faithful Pi session it can resume? The first is reconstructible from the trace; the second probably isn't.
  • Working memory and deliverables. <app>-sessions/ holds real output. Does it egress as artifacts, or is losing it acceptable?
  • State channel semantics. At-least-once with dedupe on foldSeq? What does the agent do when acks stop — proceed, or block?
  • Snapshot vs. replay. Ship the whole state doc each fold (simple, larger) or only diffs (small, needs ordered replay to rebuild)?
  • Do reducers run on Pi events or kernel trace events? Trace events are already normalized and already leave the machine — reducing over them means the same input rebuilds state offline. Reducing over raw Pi events is closer to the source but ties state to Pi's shapes.
  • Does the spool replace state.jsonl? If every fold is already spooled and shipped, a separate local state log may be redundant — unless local resume needs it without a receiver present.
  • In-memory growth on long runs. Requests stay small under projection, but Pi's array doesn't. Do we ever prune it (Pi's own context-editing/compaction), or accept the memory cost?
