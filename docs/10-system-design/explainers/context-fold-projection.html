Context fold-back & projection

Agent Kernel design explainer — working doc, updated 2026-07-25 for @earendil-works/pi-*@0.82.1

⚠ Re-measured on Pi 0.82.1 — two findings reversed. MEASURED

This doc was originally written against @mariozechner/pi-*@0.70.6. That package is now deprecated in favour of @earendil-works/pi-*, and re-running the spike on 0.82.1 shows the agent loop is now strictly sequential where it used to race:

  • Q2 reversed — turn_end now blocks the loop (it did not before).
  • Q3 resolved — the race window between turn_end and the next context no longer exists.
  • Q4 reversed — await session.prompt() now settles after all lifecycle handlers, so it is a safe end-of-run barrier. 0.82.1 also adds an explicit agent_settled hook.
  • Q1 and Q5 unchanged — context and tool_call still block; veto still works.

Consequence for the design: folding in turn_end is now viable and arguably cleaner than folding in context — see §3 and §7. Projection still has to happen in context, because that remains the only hook that can rewrite the outgoing request.

Model superseded — 2026-07-27 design interview.

The fold/projection vocabulary and the three-store framing below predate the agreed state model: one state object per agent, with the messages as part of the state (the PPO observation), a seed / update / render contract, and a three-section request (system · context · state). "Fold" corresponds to update, "project" to render. See state-shapes.html (v4) for the current model and the full decision table.

What remains authoritative here: the measured Pi 0.82.1 hook behavior (§4–§6) — every timing, blocking, and non-destructive-rewrite fact still underpins the wiring.

TL;DR. Instead of letting an agent's context be an ever-growing message transcript, the kernel keeps three things: an always-current state document, the diffs not yet folded into it, and the message history as a record. Every provider request is freshly compiled — a projection of state + unfolded diffs + a recent-message window — instead of the raw log. The maintenance step that keeps state current is fold-back, and a runtime spike has pinned down exactly where it can safely live in Pi: the context extension hook.

1. The problem PROPOSAL — problem framing

Today an agent's context is its transcript. Every turn appends; nothing is ever revised. What is true now is implicit — smeared across old messages — and stale statements sit in the request competing with their own corrections:

Two verbs carry the whole design: fold (diffs → state, so the state doc stays current) and project (state + diffs + recent messages → the request). The transcript remains the durable record; it just stops being the thing we ship to the provider wholesale.

The “request-compile point” is not an abstraction we have to invent — it is Pi's context extension hook, which fires immediately before every provider request, is awaited on the loop's critical path, and can rewrite the outgoing message array MEASURED.

Where the two verbs go, on 0.82.1. MEASURED — revised

The original version of this doc argued that both fold and project had to live in context, because turn_end raced the next request and could lose. On 0.82.1 that race is gone — turn_end blocks, and it completes before the next turn's context runs (measured: turn_end[0] ends 2528.8 ms, context[2] starts 2832.4 ms). So the two verbs can now be split, which is cleaner:

  • Fold → turn_end. It is awaited, it fires once per turn (not once per request), and its event payload already carries message and toolResults — exactly the reducer inputs. Folding here also means the fold cost is paid once per turn instead of on every provider request.
  • Project → context. Still mandatory here: it is the only hook that can rewrite the outgoing message array, and it is the only one that fires per provider request.

Folding in context still works and remains the more conservative option — it is self-healing, since the projection is recomputed from scratch every request regardless. The split is an optimisation the new ordering makes safe, not a correctness requirement.

4. When does the packet compile? MEASURED

Not once at loop start — once per provider request. In an agentic loop, that means many times per user message: one prompt with three tool round-trips compiles the packet four times. Pi's own contract says it outright — context is “fired before each LLM call,” while before_agent_start is “after user submits prompt but before the agent loop.” The spike confirms it: a single session.prompt() fired context twice (304.9 ms and 2832.4 ms on 0.82.1).

What the hook actually permits: total, non-destructive replacement. MEASURED — source-verified

The handler returns { messages?: AgentMessage[] } and Pi uses it like this (pi-agent-core/agent-loop.js):

let messages = context.messages;
if (config.transformContext) messages = await config.transformContext(messages, signal);
const llmMessages = await config.convertToLlm(messages);
  • The result lands in a local variable used only for this one request. context.messages — the session's real accumulating state — is never touched, and handlers are even given a structuredClone, so in-place mutation can't leak back.
  • So you may replace the array wholesale — drop everything, synthesize messages, stub every image — without any risk of corrupting session state.
  • But your rewrite does not feed forward: the next request's context receives the original transcript again. Projection is recomputed from scratch every time, never incrementally maintained.
  • Therefore the state doc cannot live in the message array — writes there evaporate. State and diffs must live in kernel storage and be rendered into each projection. Pi's mechanics require the three-store model.
  • Upside: projection is idempotent by construction — a pure function of (session messages + kernel stores). Even a late or failed fold can only make the next projection stale, never corrupt, and staleness self-heals on the following request.

Consequence: two injection points, two different cadences. SKETCH — open

  • System prompt (before_agent_start, ×1 per prompt) — cheap and cache-stable, but frozen for the whole loop. State folded here goes stale the moment turn 0 produces a tool result.
  • Messages (context, ×1 per request) — always current, and the only place the packet can reflect what just happened mid-loop. Costs a recompile per request, and rewriting early positions breaks the prompt-cache prefix.

This is the real knob to decide: how much of the packet is per-prompt (stable, cached) versus per-request (fresh, recompiled). It is the same trade the eviction rule cares about — and it's why fold work on the critical path has to stay cheap.

7. Open questions — where it gets weird ? OPEN

  • End-of-run drain barrier. — RESOLVED on 0.82.1. await session.prompt() now resolves after agent_end settles (measured), and Pi adds an explicit agent_settled hook: “fired after an agent run has fully settled and no automatic retry, compaction, or queued continuation will run.” No internals-poking required. New sub-question: prefer agent_settled or the prompt() return — the hook is more explicit, the return is simpler.
  • What is authoritative? If the state doc and the transcript disagree, which wins? Proposal says the state doc is the snapshot of “now” and the transcript is the record — but every consumer (viewer, traces, replay) needs to agree.
  • Diff granularity. Are diffs structured operations against a typed state doc, prose deltas, or both? This decides how mechanical fold-back can be.
  • Debug & replay. Fold-back rewrites what the model sees. Either traces capture the compiled projection per request (the request-snapshot work points this way), or the projection stays a pure, versioned function so it can be re-derived offline — pick one deliberately.
  • Fold in turn_end or in context? 0.82.1 makes both safe. turn_end fires once per turn and hands you message + toolResults directly; context fires once per provider request and is self-healing. The first is cheaper, the second is more forgiving. See §3.
  • Do we still need the request-snapshot trace? If projection is pure and versioned, the compiled request is re-derivable from the log — making per-request snapshots a debugging convenience rather than a correctness requirement.
  • Prompt-cache prefix vs. rewriting. Every fold that rewrites early message positions invalidates the provider's cached prefix — and the packet compiles once per request, not per user message (§4). This pushes toward folding at coherent boundaries rather than every request, and toward keeping the stable material in the per-prompt system prompt. Probably the main cost knob of the whole design.
  • Push vs. pull. If a tool can always return the current version (a fresh screenshot, the current file), stale copies need not ride in context at all — eviction becomes safe because retrieval is available. What is the eviction rule, and which tools must become pull-able to support it? Note the provider constraint: assistant toolCall blocks and their toolResult must be dropped as pairs, though their content can be freely rewritten to a stub.
  • Fold cost is on the critical path. The context hook blocks the loop, so every millisecond of fold work is added request latency. Cheap folds inline; anything expensive (summarization) must be prepared off-path and only applied in the hook.
  • Compaction-as-projection. If projection keeps requests small by construction, Pi's separate compaction path may become redundant — or an interference source to disable.
