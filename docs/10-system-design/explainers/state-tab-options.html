R2.2 Interaction spec AGREED — built as annotated

Selection model

  • Selectable pieces: the whole STATE block, each of its nine top-level fields, the attached-renders group, and any individual message. Coarse-grained only — no nested tree this round.
  • How you select: double-click (or ↵ on) a sidebar row; the ⤢ / Focus affordance on the board's lines; a message header's focus affordance. Single click on a rail row only scrolls (wayfinding stays cheap).
  • One selection per surface: stacked view holds at most one focused piece; in split, each lane holds at most one. Selecting another piece replaces the current focus in place — no stacking, no history maze.
  • Focused layout = breadcrumb (ZONE › piece · line range) + Back + the piece at full width with its raw-slice affordance. Views brings its renders; messages bring their images. Byte-exact rules unchanged.

As built, then cut. Selectable pieces were the whole State payload, the attached-renders group, and the message stream — each entered from its own ⤢ Focus control. None of it survives: see the REJECTED note at the top. The nine per-field targets and the per-message targets both lived on the rail and went with it. “One selection per surface”, “selecting another piece replaces the current focus in place”, and the focused layout's anatomy all shipped verbatim; single-click-scrolls / double-click-focuses was rail behaviour and no longer exists.

Back / Escape

  • Back paths: ‹ All state / ‹ All messages in the crumb, re-invoking the focused rail row, or Esc. Returning restores the resting stream scrolled to the piece you just left.
  • Esc precedence (extends the agreed §0 detail-view rule): code/image modal first → then focus (back to stream; in split, the last-touched lane's focus) → then the Details takeover. Never more than one layer per press. BUILT — one pure resolver, asserted over all eight open/closed combinations and as an ordered three-press ladder.

Sidebar REJECTED ON REVIEW

  • One index, three postures: same rows in resting, focused and split. Resting: scroll-spy underlines where you are. Focused: the selected row is marked and every other row is a one-step switch. Split: state rows target the left lane, message rows the right.
  • Message rows are sparse: the user ask and clamped/long entries get rows; short articles are reachable by scrolling, not indexed. Keeps the rail slim on a 10-message tail.
  • Narrow panels (<700px): the rail collapses to the crumb plus a jump menu; zones, captions and the crumb continue to answer “where am I?”.

Split toggle & persistence DEFERRED

  • ⫿ Split lives in the tab row; stacked is the default. The preference is per-user and persists across sessions; focus selections are per-event URL state.
  • URL: focus and split serialize onto the span route — ?span=…&tab=state&focus=state.board, focus=msg.5, and in split split=1&focusL=state.board&focusR=msg.5. “Viewing the board alone” is a shareable address; deselect drops the params; an invalid focus falls back to resting.
  • What persists across events: the active Turn tab (per §0) and the split preference. Focus does not — switching spans resets to resting (open question 4 challenges this).
  • Parse failure: BUILT no offsets → no field rows, no focus targets. The STATE/MESSAGES zones, the raw figure and message rows survive; the contract from round 1 (one captured payload, offset projections, raw one affordance away) is unchanged.

R2.3 Open questions ANNOTATED WITH WHAT THE BUILD CHOSE

  1. Message focus threshold. Focusing a one-line message is a no-op layout. Is every message selectable for consistency, or only entries that actually clamp (long tool results, the ask)? The mockups assume the latter for the rail, the former for in-stream affordances.

    Chosen: all — the simplest consistent rule, and it was the rule the rail shipped with (ten rows for a ten-message tail, every one a focus target). The rail cut then removed per-message focus entirely, so the whole message stream is now the single focusable piece on the Messages surface. If per-message focus comes back, it comes back as an affordance on the message card — which is the surface a separate round is already reworking. STILL OPEN

  2. Split at real panel widths. The detail panel commonly runs ~480–720px; two lanes under that are unreadable. Gate split behind a minimum width, or make split available only in the expanded modal / a popped-out full-window view?

    Moot this round — split is deferred, so nothing was gated. Worth noting the same width pressure is what made the rail expensive: at ~500px a 11.5rem rail took a fifth of the reading width, which is part of why it read as “hard to see what's actually going on.” DEFERRED WITH POSTURE 3

  3. Board's internal map. The 75-line board has its own structure (DESCRIPTION / BOARD tree / EDGES). Does the focused Board view get a local mini-index, or is that a round-3 question?

    Round-3 question, now upstream of itself: there is no focused Board view to give a mini-index to. The parse that would feed it exists and is asserted (board = lines 18–92, 75 lines, byte-exact), so the question survives intact — it just has to wait for per-field focus to get an entry point. STILL OPEN

  4. Focus across turns. Keeping focus=state.board while stepping turn spans would give a poor-man's board diff. That conflicts with “focus resets on span change.” Which wins?

    Chosen: reset wins, and it fell out of the existing architecture rather than being argued — the detail panel is keyed by span id, so selecting another event remounts the body and focus starts null. Persisting focus across turns would now be a deliberate addition, not a default to defend. DECIDED — RESET

  5. Sidebar beyond the State tab. If Context later grows structure, does the same sidebar pattern extend there?

    Answered by the rail's rejection: the pattern that generalizes is surfaces + per-piece focus, not a sidebar. DetailTab.zones and DetailBlockSpec.focus are tab-agnostic, so Context can grow subtabs and focusable pieces the day it has more than one block, with no new chrome. SETTLED

  6. New — how does per-field focus get back in? The rail cut removed the only way to reach “Board alone.” The three candidates: a collapsed Focus a field ▾ menu in the State figure's footer; a per-field affordance that appears on hover over a field's line range; or splitting the State surface into per-field blocks (which is round-1 direction A, already rejected as too heavy). UNDECIDED

Where images render

Selecting Views shows its byte-exact three-line slice and the three attached renders together in the same State reading pane. The images are resolved at that reference point; there is no sibling Renders block.

“Where am I?”

The lane switcher says State or Messages. Inside State, the selected tree row, breadcrumb and source line range name the field. On narrow screens the tree can collapse while the lane and breadcrumb remain.

Byte-exactness without two truths. The tree and panes are projections of the one captured <state> payload. Each node retains its source range, and Raw state opens that same payload verbatim; the browser never stores or reserializes a decomposed copy. If parsing fails, it falls back to the raw payload.

Direction C tradeoffs
+ Strongest field-level wayfinding. Board gets the whole pane, warnings become scannable on their own, and Views owns the images it names. A field can be linked directly without losing access to raw.
− Inspection is serial: showing one field clearly hides the others, so Board, Diff and Lints require navigation. The tree consumes panel width, and the separate Messages lane makes state-to-message chronology less immediate.

3. What’s orthogonal

These wins are portable to any direction; none depends on choosing its surrounding chrome.

  • Render Views in place. Resolve the three live images at <views>, not in a later sibling block. Preserve order, including the repeated close-up backed by the second occurrence of one of the two unique blobs.
  • Give Board a first-class affordance. It is 75 lines — 61% of the block — so it needs a conspicuous caption or outline entry, a stable local identity, and a focused reading surface.
  • Promote the root identity. Render v="15" · turn="5" · board="v2-flow" as a readable line that remains visible while the reader moves through fields.
  • Make Lints scannable. Lead with 0 errors · 4 warnings, then give each warning its own row instead of leaving all four as wrapped diagnostic prose.
  • Keep role identity stable. User stays blue, assistant green, tool orange and kernel muted in every Messages treatment.
  • Enforce one source contract. Every outline item, parsed card, focused pane and media anchor derives from offsets into the captured state string; raw always opens that original payload.

4. Recommendation RECOMMENDATION ONLY

Pick Direction A — Parsed State.

The deciding factor is that it fixes the reviewer’s independence problem in the main read, not only in navigation: Instruction, Scope, Board, Ops, Diff, Lints, Requests, Views and Conversation become visibly different surfaces while remaining adjacent in source order. The reader can understand the state without first operating a browser or mentally parsing 123 lines of XML.

Why not B: it is the safest evolution and the strongest verification surface, but it leaves the core burden intact. An outline can say “Board”; the reader still has to traverse the same 75-line Board inside the same 123-line figure.

Why not C: it gives the best answer to “which field am I in?” and the cleanest focused Board view, but answers by hiding every other field. That makes the relationship among Ops, Diff, Lints and Views a navigation task.

Portable across all three: render the three images at Views; preserve one immutable source string and offset-based projections; keep raw one action away; surface the root identity; special-case the 61% Board; scan Lints by warning; and keep Messages visibly outside the State field hierarchy.
