1. The thesis AGREED

Each turn, the agent is dropped into the current state and asked for the next step.

Like a policy in a PPO setup: the state is the observation, and the model is the policy. The consequence that drives everything else: the messages are part of the state. Conversation history isn't a thing that exists beside the state — it is one component of it, alongside whatever domain components exist (a board, files, a graph). There is one state object per agent, and one moving piece in every request: the render of that state.

This is what makes the design adaptable: a plain agent's state is just its messages, and it behaves like a normal agent (§3). A rich agent extends the same object with its domain (§5). Same kernel, same contract, no special cases.

2. The request — three sections AGREED

Every request the model receives is three sections, and we build all three:

① System prompt
The agent's instructions
who it is, how it works — in XML tags
changes pretty much never
② Context message
Slow accumulation
what we want visible on every request: capabilities, skills, style guides, reference sheets
rebuilt each request from a kernel-held set · entries added/removed at slow cadence (an agent can gain or lose a skill)
③ State
The moving piece
the rendered state: the working picture + however much recent conversation the renderer chooses to show
re-rendered every request by render(state)
◀ set onceslow add / removerebuilt every request ▶

Two mechanical notes that make this honest:

  • ② is rebuilt, not accumulated in the transcript. The kernel holds the L2 set (id → content) and renders it into one context message each request. Adding a skill mid-run adds an entry; losing one removes it. Nothing stale can linger, because nothing is pinned to history.
  • ③ may contain real messages. Conceptually the recent conversation is state being rendered; mechanically the renderer emits it as genuine user/assistant/tool messages, because providers require real structure for tool-call pairing and reason better over real turns. The in-flight turn is always real messages. How much conversation renders — and in what form — is the renderer's policy.

3. Base state — a normal agent AGREED — the key piece

This is the centerpiece of the kernel: an agent with no state.ts is a completely normal agent. Its state is its messages; the default renderer shows them as a rolling window. No schema, no XML state block, no ceremony — the kernel imposes nothing.

The request it receives: ① system prompt · ② context message · ③ turns 6–14 as real messages, with one elision marker where history was cut ([turns 1–5 elided]). Cuts land only on turn boundaries — an assistant toolCall and its toolResult are never split, because providers reject orphaned halves.

That's the whole base behavior. It reads like a normal agent transcript because it is one — just bounded. Old images past a newest-K cap become one-line stubs before old turns drop entirely. There is no compaction step anywhere, because nothing ever piles up to compact.

Window policy is per-agent configuration, not a kernel rule. AGREED The kernel ships sizing strategies — turn count, token budget, more as needed — and each agent's config picks and tunes one. The pair-safe turn-boundary cut is the only invariant. Defaults are a build-stage decision.

6. The bundle tree — one agent, vertical slices AGREED — built 2026-07-27

These are the four sections of an agent: the prompt, the context, the state, the tools — and the bundle mirrors the request: read the tree top-to-bottom and you read the request left-to-right. Instead of horizontal repo layers (all loaders together, all styles together, nothing attributable), everything that defines one agent is one vertical slice, narrowed by runtime role — the prompt is the system prompt, the context is how the agent gets and declares its standing context, the tools are auto-exposed from their folder, and the state is the actual logic for how each turn is handled.

catalog/layout-editor/
├── agent.json                  ← the index: model, thinking, maxTurns, window
├── prompt/                     ← section ① — the system prompt
│   ├── prompt.json               ←   SOURCE OF TRUTH
│   └── system.md                 ←   rendered markdown, generated FROM the json — for reading & diffs, never hand-edited
├── context/                    ← section ② — reference; stable for the run
│   ├── index.ts                  ←   the complete inventory of ② (defineContext)
│   ├── capabilities.gen.ts       ←   recipe → <capabilities> (generated from validator schemas)
│   ├── style-guide/              ←   authored topics
│   ├── exemplar.ts               ←   recipe: house-style reference image (spawn-rendered)
│   └── contact-sheet.ts          ←   recipe: vocabulary sheet (spawn-rendered)
├── tools/                      ← the action surface — auto-registered from the folder
│   ├── apply-operation.ts
│   ├── look.ts
│   └── lint.ts
└── state/                      ← section ③ — how each turn is handled
    ├── index.ts                  ←   defineState: wires shape + rules + render
    ├── shape.ts                  ←   the state type S + seed()
    ├── rules/                    ←   update(): one file per event concern
    │   ├── operations.ts         ←     apply_operation events → the ops ledger
    │   ├── views.ts              ←     look events → view refs
    │   └── lints.ts
    └── render/                   ←   render(): one file per block of ③
        ├── board.ts              ←     the <board> digest
        ├── ops.ts                ←     <ops> / <diff>
        └── tail.ts               ←     the real-message tail via the window policy

The rules of the tree:

  • prompt.json is the source of truth. system.md is its rendered form, generated json → md so the prompt is always readable and diffable as markdown.
  • context/index.ts is the single inventory of ②. Every block and image the agent always sees is declared there — including spawn-rendered artifacts, which live in the folder as recipes (the contact sheet is a PNG that exists only at runtime; what the bundle owns is the declaration that produces and attaches it).
  • Tools auto-register from their folder. The folder is the roster; nothing lists them twice.
  • The tools↔rules↔render symmetry: tools/apply-operation.ts defines an action; state/rules/operations.ts defines what that action makes true; state/render/ops.ts defines how that truth is shown. One concern, three files, same name.
  • Scale-down rule: every folder collapses to a single file. state.ts alone stays legal; a base agent is just agent.json + prompt/ — the absence of the other folders is the statement that it's a plain windowed agent.
  • Sharing is the rule of two: an asset lives in one agent's bundle until a second agent needs it, then the bytes promote to catalog/_shared/ — but each consumer still declares it in its own context/index.ts. Library code (digest, doc-diff, loader machinery) stays in src/; the test is "does this feed a section of this agent's request, or is it machinery any agent could run?"

As built (2026-07-27): the tree above is now real. The kernel registry resolves both forms (registry/bundle-layout.ts), agent-kernel-render-prompts generates system.md byte-for-byte from prompt.json via prompt-kit, doctor --catalog audits layouts, and every bundle in both repos is folder-form — the canvas layout-editor's actual tree matches this sketch, with capabilities/ nested under context/, a per-block state/render/, and the 13 typed mutators kept in one tools/apply-operation.ts (their specs are already a single shared roster; thirteen stub files would be a second one).

Resolved at approval: discovery accepts both forms, file first (state.ts before state/index.ts, prompt.json before prompt/prompt.json) so re-export shims are safe mid-migration, with a doctor warning when both exist · prompt/system.md is generated json → md, checked in, never parsed · loader implementations stay app-registered; bundles hold declarations · the canvas catalog migrates immediately (the layout-editor is the exemplar).

8. Persistence & the turn view AGREED

  • state.json snapshot only in v1 — written after each update batch under .agent-kernel/state/<container>/<agent>/, through the sink seam. No action log, no artifact byte-store yet. This is also what enforces JSON-serializable state from day one, and what makes the state inspectable as a file.
  • Full request snapshots stay, and gain section tags. The builder marks where ① ② ③ begin, so the per-turn viewer renders the exact context window the model ran on as three sections — the turn renderer. No hash-receipt demotion.
  • Resume means multi-prompt continuity, not crash recovery. A long-running session takes message after message; state lives in the extension across prompts and update keeps folding. Crash recovery is explicitly out of scope for v1.

9. Transport AGREED — designed with v1, remote sink built in the sandbox stage

Emittraces, snapshots, and state updates all go through the one sink interface
→
Local sink (v1)trace.db + state.json — today's writers behind the seam
→sandbox stage
Remote sinkspool file → drain loop → POST; acked state channel (version-deduped), droppable observability channel

Getting runs, traces, and state out of a sandbox is part of this design, not an afterthought — but it lands as its own stage, after the state model is verified. Because everything already emits through one seam, the sandbox story is a sink swap, not a rework. Details live in prompt-cache-tiers.html.
