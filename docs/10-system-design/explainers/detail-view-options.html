Text that does not parse as JSON is rendered unchanged.

Declarative Turn grouping. System prompt, context and state remain standard data-only blocks. The Turn renderer groups them into four tabs (originally three; revised 2026-07-28 to add the tool roster last), while the shell owns the tab bar, active state, block ordering and modal expansion.

Simplicity in the main read. The main read carries NO tokens, hashes or technical extras; all of that lives in the full-panel Details view.

0. The layout standard AGREED 2026-07-27

The standard — every event type, no exceptions

  1. Header — kind-tinted glyph + title + a quiet Details control. Identical geometry for every type; tint and glyph match the tree row. Its fixed h-12 surface is shared with the tree toolbar: bg-muted/40 over border-b border-border. Event type and duration are in the Details view. Opening Details preserves the same header geometry and replaces only the control with an accessible X.
  2. Body (blocks, or tabs of blocks) — always non-empty and composed ONLY from the standard block vocabulary, in a fixed slot order. Non-Turn bodies are untabbed. Turns use four shell-owned tabs in the fixed order State | Context | System prompt | Tools (originally three; Tools added 2026-07-28), defaulting to State; the tab row is one segmented control, and slot order is enforced separately inside each tab. Every block keeps the same doc-figure, clamp and modal capabilities.

Full-panel Details takeover (revision 2026-07-27). This explicitly supersedes the earlier “Details drawer — always last, always collapsed” decision. The normal structure ends after the body: no disclosure row, bottom border or drawer spacer remains. The header's real Details button, with an accessible name and aria-expanded, replaces the body with a shell-owned Details view for the selected event.

The header does not move. The kind-tinted glyph and event title remain on the same shared surface at the same height; an accessible X occupies the Details control's position. Focus moves into Details on open and returns to the Details button on close. X or Esc restores the normal body exactly as it was, including the active Turn tab.

Modal Esc precedence is explicit. When a code expansion or image modal is above Details, Esc closes the modal and leaves Details open. Esc closes Details only when no modal is open.

The relocated content is complete. Details carries identity (span id, event type and every attribute with per-row copy), timing (start, end, duration, span type and status), usage when present (input, output, cache-read and cache-write tokens, model, cost and stop reason), and raw span JSON without children. Multi-line raw strings remain real lines, and raw uses the standard code-block component with its gutter, zebra treatment, byte-exact rendering and ⤢ expansion.

One code-block component (revision 2026-07-27). Every data block app-wide uses the same CONFIG-pane substrate: a non-selectable line-number gutter, subtle theme-aware zebra striping, and syntax colors appropriate to its content type. The component and its modal render byte-identically with wrap off; this is the only mode, not a selectable option. Long lines scroll horizontally inside the figure and never widen the panel.

Caption rows contain the caption and expand control only (revision 2026-07-27). Counts and other metadata do not appear there; this supersedes the earlier caption-meta note. Expandable figures place a comfortable keyboard-reachable ⤢ control at the far right, replacing the bottom “Open in modal” link. Short blocks retain no expansion control. The shell owns this chrome from the block's declarative expansion capability.

Natural-language message prose is the single deliberate exception. Conversation text stays wrapped prose for readability. Tool-call arguments, tool results, prompts, context, state, lineage payloads, raw JSON and every other structured or data-bearing block use the one code-block component.

Non-empty-body guarantee (revision 2026-07-27). There is no summary tier. Every event renders at least one standard block; for a tabbed body, the default tab contains at least one. Fact-only events use a compact facts block, so the plain-language event information remains in the main read and dead ends are structurally impossible.

The block vocabulary

SlotHoldsReal examples
inputparams, declared inputs, the instructionthe update_sticky argument table; Declared inputs; Loaded
contentturn sections, rendered context, message contentSystem prompt, Context with its inline images, State with attached renders at message position, Rendered context
outputresult, delta, lintsthe APPLIED · update_sticky result with its DELTA and LINTS lines
mediastandalone renders and imagescanvas-contributed render blocks on tool spans; the slot remains available even though Turn images render in place

The shell sorts blocks by this slot order. A renderer's own array order is not respected across slots — that is deliberate.

The enforcement rules

  • Per-type renderers may ONLY select blocks and fill them. Never new chrome, never new layout primitives, never a second panel.
  • Every renderer returns a non-empty body. A type with only facts fills a standard facts block; that is the fact card, not a special case.
  • Extensions (canvas) register named blocks into the body. For a tabbed view they merge into the first, default tab and follow the same slot ordering. Nothing else. No second panel, ever.

How it is enforced, not merely documented

  1. The API makes deviation impossible. A per-type renderer returns DATA, not JSX: a DetailView with exactly one of an untabbed block list or declarative tab groups. The shell owns the header, Details button and takeover state, tab chrome and interaction, block ordering, disclosures, modal expansion and Esc precedence. A renderer therefore physically cannot emit chrome, render or toggle Details, bypass the takeover, reorder slots, or open a second panel.

  2. A conformance test iterates every registered renderer and the fallback over representative real spans and asserts: header present; a real Details button with the correct ARIA; at least one standard block in an untabbed body or in the default tab; exactly one body form; body children carry the standard roots and non-decreasing slot order within each tab; the first tab is active when tabs exist; no bottom drawer chrome; and no renderer-owned chrome outside the vocabulary. The exported Details view is also rendered directly for each span to prove the required identity, event type, timing, duration, attributes and standard raw code block, plus usage when the span carries it. This non-empty-body assertion is what makes dead ends structurally impossible. The test reads the registry programmatically, so a renderer added later is covered automatically.

3.4  Is PRIMARY / METADATA / RAW the right chrome?

ConfirmedNo. Two of the three tabs are actively broken, and the split is by data provenance rather than by question being asked.

RAW is unusable for any span that carries text. measured RawTab runs JSON.stringify(span, null, 2) and JsonViewer puts one line per table row with whitespace-pre. A system_prompt_resolved span serializes to 7 lines, one of which is 18,890 characters wide, because the 303-line prompt is a single JSON string with escaped newlines. The tab renders a nearly-empty box with 18,890 characters of horizontal scroll.

METADATA is load-bearing for seven event types and yet it is the tab you have to remember to click. It is also lossy where it matters: attribute values render in a truncate span with no title, so prompt_hash and content_hash — the two attributes whose whole purpose is to be compared — are cut off with no way to read or copy them.

The split is wrong in principle. Tabs should separate questions, not sources. "What did this do?" (PRIMARY), "when did it happen and how big was it?" (METADATA) and "what does the record look like?" (RAW) are not three questions a person asks in sequence — the first two are one question, and the third is a debugging escape hatch that should be attached to whatever block you are looking at, not to the whole span.

4. Cross-cutting problems measured

  1. The resolved prompt has three different renderings and none of them is authoritative. system_prompt_resolved gets prompt-kit's PromptView (highlighted, numbered, 303 lines, no outline). The Turn's System prompt section gets a plain <pre> clamped to 5 lines, collapsed by default. Canvas's ContextWindowOverlay reconstructs a third version client-side from the transcript. Ford's question — "the prompt it was resolved as" — is answered three times, differently, and the version attached to the turn (the one that proves what the model saw) is the ugliest and the most hidden.
  2. The context lineage is scattered across three spans, two trace levels, and two tabs (§3.3). There is no single view where declared → loaded → rendered → what the model got reads as one chain, even though every link exists in the data.
  3. Per-turn economics are invisible. pi_turn_end's usage payload never reaches a span. You cannot see, on a Turn, how many tokens it cost or whether the context was served from cache — which is precisely the number that tells you whether the "rebuilt each request" context design is working.
  4. Two competing implementations of "the full prompt for this turn." The kernel captures the real thing (pi_request_snapshot + blob store + GET /runs/:runId/turns/:n/context) and RequestSnapshotRenderer renders it. Canvas reconstructs an approximation client-side from the transcript in ContextWindowOverlay, reached by a button on the second tool panel. Same question, two answers, different fidelity, and the reconstructed one is the more discoverable.
  5. Extensions bolt on instead of plugging in. The renderSpanDetail seam takes over the whole column, so the only thing canvas can do is stack a second panel under the first. There is no way to say "add a Thinking block to the standard tool view" or "add an Images block."
  6. The section-label vocabulary has already forked. viewer-ui exports SECTION_LABEL_CLASS (text-[10px] … tracking-[0.14em]) with a comment saying it is "the ONE section-label style." Canvas's TranscriptInspector defines PANEL_SECTION_LABEL (text-xs font-medium) and CHROME_LABEL (font-mono text-[10px] font-bold); ContextWindowOverlay defines a fourth. Four "section label" styles render in one scroll column. That is the visible cause of "does not feel very cohesive."
  7. Nothing links to anything. A Turn cannot jump to the system-prompt event it resolved from, or to its context build, or to its pi_turn_end. A tool call cannot jump to its Turn. Every relationship is reconstructed by the reader from tree position.

Direction A — “The read”: one scroll, no tabs SKETCH

The rule: a detail panel is a document about one event, read top to bottom. There are no tabs. Everything the event has appears in reading order, in one scroll. A sticky outline rail on the right lists the blocks that exist and scroll-spies; it is the only navigation. Metadata collapses into a one-line fact bar under the title, with the long tail behind a "Facts" disclosure at the very bottom. Raw stops being a tab and becomes a { } affordance on each block — you never want the raw of the span, you want the raw of the block you are staring at.

Not chosen: a uniform document is the right shape for a Turn and the wrong shape for a tool call, which is a comparison and wants adjacency.

What you see, per event kind

Every event renders the same skeleton — header → fact bar → ordered blocks → Facts disclosure — and the only thing that varies is which blocks exist. A lifecycle event has one block ("Outcome"), a Turn has eight. Nothing ever dead-ends, because the fact bar always has content.

Prompt & context lineage

Both are just blocks in the document, in request order, so the Turn reads as ①②③. The prompt block leads with hash + "unchanged since turn 0" and offers its own tag outline; the context block leads with the resolved-input line and links out to the build. The lineage is served by adjacency rather than by a dedicated view.

The state-block width answer

Break out of the reading column. The state block is the one element allowed to span the full panel width including under the outline rail (negative margins to the panel edge), with three controls in a strip above it: wrap (on by default — soft-wrap with a hanging indent so containment depth survives the wrap), byte-exact (turns wrap off, restoring today's whitespace-pre for verification), and focus (promotes the block to a full-window overlay for reading a 40-object digest properly). Clamp becomes height-based, not line-based, so a 123-line block with short lines is not truncated as aggressively as a 123-line block of 400-char rows.

Direction A tradeoffs
+ Cohesion comes for free — one skeleton, one label vocabulary, no chrome to get out of sync. Kills all three tab problems at once. The Turn finally reads as the three-section request. Extensions contribute blocks, so canvas's thinking/images fold in and the double-render disappears structurally.
− A Turn becomes a very long scroll; the outline rail carries almost all the navigation load and costs ~130px of a panel that is already only 60% of the width. No side-by-side comparison of any kind. "Collapsed by default" decisions become high-stakes because there is nowhere to hide anything.

Direction B — Purpose-built layouts per event kind, under a shared shell AGREED — building 2026-07-27

The rule: the shell is fixed and thin — identity header, breadcrumb, fact bar — and the body is designed for the question that event kind answers. A Turn is a reading problem, so it gets a reading layout. A tool call is a call → result problem, so it gets a paired layout. A context build is a provenance problem, so it gets a lineage layout. There are ~5 bodies, not 15; everything else falls to a generic fact card that is still never a dead end. Extensions register named blocks into an existing body, never a second panel.

Directly served, and the strongest of the three on this axis. The state-block width answer

Width priority: the state block wins the panel. In the Turn layout it renders full-bleed edge to edge, and ①/② are compressed to a line and a strip precisely so it can. Soft-wrap with hanging indent is the default (indent depth preserved on continuation lines), byte-exact toggles it off, focus opens a full-window reader, and a "Jump:" strip lists the block's own top-level tags (scope · board · ops · diff · lints · requests · views) so a 40-object digest is navigable rather than scrolled. Direction B tradeoffs
+ Each event finally gets a layout that fits its question; the Turn's information hierarchy becomes correct (③ is the moving piece, so ③ gets the space). Kills the double-render by construction. The lineage view is the only thing in any direction that fully answers Ford's context question. Fact cards eliminate all seven dead ends.
− Most work: ~5 bodies to build and keep visually coherent, and drift between them is exactly the failure that produced today's four section-label vocabularies. Needs a genuinely enforced shared component set (one heading, one collapsible, one mono block, one thumb strip) or it degrades within two features. A new event kind needs a decision, not just a registry line.

The rule: keep a switcher, but make it honest. A structured header that never scrolls away carries identity, status and the 4–6 facts that matter for that kind. Facets are deep-linkable, so "open turn 4's state" is a URL. Extensions register facets — canvas's transcript inspector becomes a facet named Renders, not a second panel; ContextWindowOverlay is deleted in favour of the Turn's own facets.

Not chosen: it fixes which tabs exist without fixing that tabs hide things, so ①②③ would never be seen as one request.

What you see, per event kind

The facet set is the IA rule: a facet exists if and only if the event has content for it. That makes the bar a summary of the event before you click anything ("this turn has a state and a response but no images"), and it makes dead ends structurally impossible — an event with only a record shows a fact card with no bar at all. Facet names come from a fixed vocabulary so Result means the same thing on every kind.

Prompt & context lineage

The prompt hash rides in the persistent header, so "what was it resolved as" is answered without navigating, and the Prompt facet holds the full resolved text at turn fidelity. Lineage is weaker than B: Context is one facet, so declared/loaded/rendered have to be stacked inside it rather than shown as a chain — you would want the lineage strip from B as the facet's header.

The state-block width answer

Dedicated expansion. Selecting the State facet gives the block the entire panel body — no competing sections, no rail — and a ⤢ wide control in the facet bar collapses the span tree to an icon rail so the panel takes ~85% of the window for as long as you are reading. Wrap-on-by-default with a byte-exact toggle, same as the other two. This is the cleanest answer of the three for reading, and the worst for context: you cannot see the state and the response at the same time.

Direction C tradeoffs
+ Cheapest evolution from today (TabShell already exists; the change is "derive the tabs, promote the facts, add a header"). The facet bar doubles as a content summary. Deep links are a real workflow win for "look at this turn's state" in review. The extension seam becomes a facet registration — canvas plugs in instead of bolting on.
− Still chrome. It fixes which tabs exist without fixing that tabs hide things: the Turn's ①②③ are three facets, so the three-section request is never seen as one thing — which is the single most important thing the panel has to show. Header + facet bar cost ~90px of vertical space on every event. Variable tab sets can feel unstable as you move down the tree.

7. Recommendation AGREED 2026-07-27

Direction B, built on Direction A's spine.

This is what is being built: purpose-built bodies per event kind (B), with each body's section renderers stacked in a single scroll with no inner tabs (A), because the one thing the panel most needs to do — show that a request is ① prompt + ② context + ③ state — is destroyed the moment those three become tabs or facets. A section header isolates its renderer full-panel with a breadcrumb back. C's best idea, the extension registers a named block/facet instead of taking over the column, becomes the seam rule for both. C's ⤢ wide control is absorbed into isolation.

Why not A alone: a uniform document is the right shape for a Turn and the wrong shape for a tool call. A tool call is a comparison — these arguments produced that result — and comparisons want adjacency, not sequence. B's pair layout says that in one glance; A's block sequence makes you scroll between the two halves of one thought.

Why not C alone: C is the cheapest and it fixes the tab membership problem, but it does not fix the tab premise. Splitting ①②③ across three facets means the panel never once shows the request as a request, which is the thing Ford is actually asking for.

What makes B survivable (its real risk is drift, and drift is what produced today's mess): a small, exported, enforced component set that all bodies compose — SectionRule, FactBar, LongBlock (the one clamp contract), ArgsTable, ThumbStrip, LineageStrip, FactCard. Seven components. If a body needs an eighth, that is the review conversation. Canvas imports them and registers blocks; it never defines a heading style again.

Build order AGREED — the first-round §6 items are sequenced first because they are cheap and they de-risk the layout work:

  1. Builder truth: carry pi_turn_end usage onto the Turn and keep end.inputs[]; handle the attachment badge viewer-side.
  2. The seven shared components + one clamp contract; BaseRenderer → fact card (seven dead ends fixed).
  3. First-class system-prompt, context and state renderers: doc-style figures stacked in reading order, each isolatable full-panel.
  4. Tool body: pair layout with thinking + images as blocks; delete canvas's second panel and ContextWindowOverlay; add cross-links.
  5. Collapse span raw JSON, usage/tokens, hashes, timing and per-block raw into the Details drawer; retire PRIMARY/METADATA/RAW.
